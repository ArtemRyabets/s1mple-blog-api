# Звіт до Лабораторної роботи №7: Performance Analysis

## 1. Методологія тестування
- Інструмент навантаження: k6
- Сценарій: Емуляція 10 одночасних користувачів (VUs), які активно роблять запити до API.
- Інструмент профайлінгу: Clinic.js Doctor

## 2. Результати тестування
Під час запуску навантажувального тесту сервер продемонстрував нестабільну роботу.
Clinic Doctor зафіксував проблему та видав діагноз: Detected a potential I/O issue (Проблема вводу-виводу).

Основні показники:
- CPU: Високі сплески навантаження на початку, але процесор не був вузьким місцем постійно.
- Event Loop Delay: Значні затримки в обробці подій.
- Memory: Споживання пам'яті стабільне, витоків (Memory Leak) не виявлено.

## 3. Аналіз запитів до БД
Для детальнішого аналізу було увімкнено логування запитів Prisma (log: ['query']).
Було виявлено, що при кожному запиті API виконується важка операція агрегації даних у MongoDB:
prisma:query db.Post.aggregate(...)

## 4. Висновок
"Вузьким місцем" (bottleneck) системи є модуль роботи з базою даних (post.service.ts).
Сервіс створює нове підключення або виконує неоптимізовані запити, що призводить до блокування Event Loop під навантаженням (I/O Wait).

Для вирішення проблеми у Лабораторній №8 було вирішено:
1. Винести логіку роботи з БД в окремий шар.
2. Використати Dependency Injection для управління підключенням PrismaClient.
